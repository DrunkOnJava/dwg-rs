# Clean-room policy

`dwg-rs` is developed clean-room from public specifications and
first-party byte inspection of publicly-available DWG files. This
document describes which sources are allowed and which are not, and
how contributors should certify compliance in pull requests.

It exists because the DWG ecosystem has a long history of licensing
disputes and multiple permissively-licensed efforts have been
complicated by upstream source contamination. Writing this policy
down makes the project's posture auditable by legal reviewers and
defensible against future claims.

## Allowed sources

Contributors may consult and cite any of the following while
developing `dwg-rs`:

- The **Open Design Alliance's freely-redistributable** *Open Design
  Specification for .dwg files* (v5.4.1 or later). This is a public
  PDF at
  [opendesign.com/files/guestdownloads/OpenDesign_Specification_for_.dwg_files.pdf](https://www.opendesign.com/files/guestdownloads/OpenDesign_Specification_for_.dwg_files.pdf).
- **Public academic papers** on CAD file formats, the LZ77 family,
  Reed-Solomon codes, and related algorithms.
- **Publicly-available DWG files** whose terms permit use for
  interoperability testing (e.g., the MIT-licensed `samples/` of
  `DomCR/ACadSharp`, or sample files released by organizations that
  allow third-party consumption). A public file that states no licence,
  such as `nextgis/dwg_samples`, is fetched for a run by pinned hash and
  never redistributed. The files CI reads, their licences and their
  status are under "Public corpus" below.
- **Self-generated byte fixtures** written by hand to exercise
  specific decoder code paths.
- **Algorithm descriptions** in permissively-licensed projects
  (ACadSharp comments, LibDXF documentation, academic thesis work).
  Only the high-level algorithm description — never the implementing
  source code.
- **Standard Rust crates** on crates.io that are either Apache-2.0,
  MIT, or dual-licensed and compatible with Apache-2.0
  redistribution.
- **Rust language reference and standard-library docs**.
- **Hex editors, binary-diff tools, and disassemblers** applied to
  publicly-released DWG files — for **understanding format
  structure**, not for reverse-engineering Autodesk's or ODA's
  implementation binaries.

## Forbidden sources

Contributors must **not** consult, port, adapt, or quote from any of
the following while writing code for `dwg-rs`:

- **Autodesk SDK source code** — RealDWG, ObjectARX, ObjectDBX, or
  any other Autodesk-distributed SDK, whether or not the contributor
  has signed an NDA or developer agreement.
- **Open Design Alliance (ODA) SDK source** — "Drawings SDK" /
  "Teigha" / successor products. The ODA's *specification PDF* is
  explicitly allowed (see above); the ODA SDK source is explicitly
  forbidden.
- **LibreDWG** — GPL-3-licensed; source inspection would taint this
  crate's Apache-2.0 license.
- **Decompilations of Autodesk or ODA binaries** (AutoCAD,
  ObjectARX.dll, Teigha_*.dll, etc.).
- **Leaked or unofficial Autodesk / ODA documentation** that is not
  the public *Open Design Specification* PDF.
- **Any DWG implementation code whose license is GPL, LGPL, AGPL,
  SSPL, or proprietary** — including snippets found on Stack
  Overflow, GitHub Gists, or archived forum posts if the code
  lacks a permissive license.

## Contributor declaration

Every pull request that adds or modifies decoder / encoder logic
must include a declaration in the PR body. The PR template includes
a checkbox for this; the text of the declaration is:

> **Clean-room declaration.** I certify that:
>
> 1. All code and tests in this PR were written from scratch by me
>    or other individuals listed as co-authors.
> 2. I consulted only sources listed as allowed in `CLEANROOM.md`.
>    In particular, I did not consult Autodesk SDK source, ODA SDK
>    (Drawings SDK / Teigha) source, LibreDWG source, decompilations
>    of Autodesk or ODA binaries, or any copyleft-licensed DWG
>    implementation code.
> 3. Where this PR cites a reference (ODA spec section, algorithm
>    description, public paper), the citation is included in the
>    diff as a comment or doc link.
> 4. If I have ever had access to any of the forbidden sources in a
>    commercial or NDA'd context, I have disclosed that in the PR
>    discussion and the maintainer may mark this PR as needing
>    additional review.

A PR that cannot include this declaration truthfully will be
declined. Reviewers are asked to treat the declaration as load-
bearing: if something in the diff looks suspiciously close to a
known forbidden source, the PR is blocked until the author can
demonstrate clean-room provenance.

## For legal reviewers

If you are evaluating `dwg-rs` for commercial adoption and need to
audit the clean-room process end-to-end:

- Every merged PR passes through the declaration above. The
  `.github/PULL_REQUEST_TEMPLATE.md` file is the canonical form.
- `CONTRIBUTING.md` reiterates the rule from the contributor
  workflow angle.
- `NOTICE` summarizes the third-party authority (Sega v. Accolade,
  Sony v. Connectix, Baker v. Selden, etc.) that supports
  independent file-format reverse engineering for interoperability
  — this is context, not a legal opinion.
- `SECURITY.md` and `THREAT_MODEL.md` are separate documents
  governing vulnerability handling.

For direct questions about the clean-room posture, open a GitHub
Discussion or email the maintainer. For legal questions about
whether this project is safe for your specific use case, consult
your own counsel.

## 2026-04-19 — LZ77 offset encoding (ACadSharp algorithm comments, MIT)

Commit 3300303 ("Phase B — LZ77 decompression") resolved an ambiguity in
the spec's §4.7 description of compressed offsets. The spec text gives the
long form as "+0x3FFF" and the short form as "+0"; files produced by
AutoCAD decompress correctly only if every offset class is one larger:
+0x4000 for the long form, +1 for the short form, +1 for the 0x40-0xFF
opcodes, with bit 3 of a 0x10-0x1F opcode supplying bit 14 of the offset.
These rules were cross-checked against the algorithm-description comments
of the MIT-licensed ACadSharp reader, which `src/lz77.rs` cites where they
apply. No ACadSharp source code was copied, translated or structurally
followed; the comments were used only to confirm the offset arithmetic.
This is the one reading of another DWG implementation that the README,
`src/lib.rs` and ARCHITECTURE.md refer to. It was not recorded here when
it happened; this entry was added on 2026-10-26 from the commit and the
code comments.

## 2026-08-30 — VISUALSTYLE property names (Autodesk public DXF Reference, recalled)

PR #47 derives the R2010+ `VISUALSTYLE` field layout entirely from bytes: the
one token sequence over `B/BS/BL/BD/CMC` that lands every record of a file
exactly on its string-stream start bit (24/24 records per file, delta 0), with
decoded values cross-checked against AutoCAD's Visual Styles Manager. The
**names** given to the 28 (R2010) / 58 (R2013+) value/flag slots follow the
conventional `AcDbVisualStyle` property ordering as recalled from Autodesk's
public *DXF Reference* (published documentation, not SDK or product source).
Only the face-group names are independently corroborated by values; the
edge/display names are positional labels and may be renamed if a later file
contradicts them. No code, structure, or layout was taken from that document —
it contributed vocabulary only. ODA spec v5.4.1 has no VISUALSTYLE or MATERIAL
section; the `§19.6.9` / `§19.6.10` citations previously in this tree were
withdrawn in the same PR.

The PR for #48 extends `VISUALSTYLE` to the R2004 band and needs **no
new outside vocabulary at all**. Its field list was derived from bytes
the same way — the one token sequence that lands all 24 records of each
of `arc_2004.dwg`, `circle_2004.dwg` and `line_2004.dwg` exactly on
their `RL` object-data-size boundary — and every name on it is carried
over from the R2010 list disclosed above, justified slot by slot
against the value the *same style* decodes on `arc_2010.dwg`. The one
slot with no R2010 counterpart is labelled `edge_unknown_byte`, and the
13-bit run it leads is documented as a run whose internal boundaries
the corpus cannot separate rather than being split into invented
fields. R2007 is declined outright: no `AC1021` object reaches a
decoder in this crate, so nothing is claimed about that band.

## 2026-08-30 — LAYOUT / PLOTSETTINGS field names (ODA spec §20.4.84)

PR for #50 replaces the LAYOUT and PLOTSETTINGS field lists. Unlike
VISUALSTYLE above, this one needed no outside vocabulary: **§20.4.84
LAYOUT** of the freely-redistributable ODA *Open Design Specification
for .dwg files* v5.4.1 prescribes the whole record — the plot-settings
block (each row glossed `plotsettings …`) followed by LAYOUT's own
fields — and every field name, type and DXF group code in
`src/objects/acad_layout.rs` and `src/objects/acad_plot_settings.rs`
comes from that table. No Autodesk DXF Reference wording was consulted
or needed for this object, and no code, structure or layout was taken
from any source outside the spec PDF and the corpus bytes.

Two departures from the spec are **measured**, not borrowed: the
record's `viewport_count` is a `BL` where §20.4.84 prints `RL`, and the
R2013+ `has_ds_binary_data` flag is followed by 16 further bits where
the spec's common-object-data table names only the `B`. Both are
derived from the corpus's own data-stream boundary and documented in
the modules; neither came from a third-party implementation.

The "§19.6.12 (L6-12)" and "§19.6.6 (L6-14)" citations the two modules
previously carried are withdrawn — the spec has no §19.6 chapter, and
§20.4 carries no standalone PLOTSETTINGS entry.

only, and the slots whose decoded values do not corroborate a name are

`MLINESTYLE` needed no outside vocabulary: **§20.4.73 MLINESTYLE** of

## 2026-08-30 — ACIS entity record (ODA spec §20.4.41 + §24)

The PR for #61 decodes the whole `REGION` / `3DSOLID` / `BODY` record.
Both halves of it come from the freely-redistributable ODA *Open Design
Specification for .dwg files* v5.4.1 and from the corpus bytes:

- **§20.4.41 REGION (37) / 3DSOLID (38) / BODY (39)** prescribes the
  record in one table for all three entities — the ACIS envelope
  (`ACIS empty` bit, unknown bit, `BS` version, the version-1 block
  loop), the wireframe / point / isoline block with its wire and
  silhouette structures, the second `ACIS empty` bit, and the R2007+
  trailing `BL`. Every field name and type in
  `src/entities/modeler.rs`, `three_d_solid.rs`, `region.rs` and
  `body.rs` comes from that table, including the spec's own gloss
  "Normally 1" on the second empty bit. Two departures the previous
  code carried — a missing `B unknown` bit and a fabricated
  `B has_more_blocks` flag inside the block loop — are corrected
  *toward* the spec, not away from it.
- **§24.2.2.3** supplies the semantics of the R2013+ shape: "For each
  ACIS entity (REGION, 3DSOLID), a data record is created with the SAB
  stream of the object." That is why the three corpus records carry no
  inline envelope.

The R2013+ data-store block that follows — seven bits, sixteen bytes,
a `BL` — is **measured**, not borrowed: it is the residue between the
end of the §20.4.41 grammar and each record's own data-stream boundary,
and the sixteen bytes are identified as a revision GUID because they are
a valid RFC-4122 version-4 UUID on all three records at the one
alignment that fits. The seven bits are labelled `unknown_*`; only their
width is claimed. The slot names that are claimed — point, isolines,
wires, silhouettes, revision GUID — are the spec's own vocabulary plus
the one word the UUID structure earns.

The `has AcDs binary data` width settled in the same PR (#54) is
likewise measured from the corpus's own boundaries: 0 bits on the
entity path, with the 16 bits four R2018 LAYOUT records need relocated
into LAYOUT's own field list. No third-party implementation was
consulted for either.

## 2026-08-30 — the R14 / R2000 / R2007 containers (ODA spec §3, §5, §20)

The PR for #104 / #110 / #65 opens the three release bands that had no
object walk. Every structure in it comes from the freely-redistributable
ODA *Open Design Specification for .dwg files* v5.4.1 and from the
corpus bytes; no third-party DWG implementation was consulted for any
part of it.

- **§3.1 / §3.2.6** prescribe the R13-R15 file layout and the
  section-locator records, including the record numbering this crate
  maps onto the canonical `AcDb:` names.
- **§5.1 - §5.4** prescribe the whole R2007 container: the meta-data
  table, the Reed-Solomon-and-compressed file header with its 34 named
  fields, the `GetSystemPageSize` pseudo-code, the page-map
  accumulation loop, the section-map record layout and the per-section
  hash codes this crate checks itself against.
- **§5.10** prescribes the R2007 LZ variant — the opcode switch of
  `ReadInstructions`, the literal-length escape, and the sub-block
  table `src/r21_lz.rs` transcribes as `COPY_BLOCKS`.
- **§5.13** prescribes the two Reed-Solomon configurations and the
  interleaving rule.
- **§19.1** prescribes the string-stream trailer that R2007 is located
  from; **§20.1** and **§20.4.1** prescribe the R13/R14 object and
  entity prefixes; **§20.4.21 / .44 / .45 / .52 / .54 / .58 / .64 /
  .68** prescribe the LINE, DICTIONARY, DICTIONARYWDFLT, BLOCK_HEADER,
  LAYER, LTYPE, VPORT and DIMSTYLE field lists this PR corrects toward
  the spec.

Four readings in the diff are **measured**, not prescribed, and each is
documented at the module that owns it:

1. The §5.10 sub-block table is applied **recursively** — the blocks
   are the smaller copy functions, so a two-byte block is reversed.
   The spec prints the table and says the byte order differs but does
   not say the blocks nest. The corpus does: two independent literals
   (the file header's first, and one inside the section name
   `AcDb:AppInfoHistory`) decode correctly only under the recursive
   reading, and under it every constant §5.2 documents comes back.
2. The Reed-Solomon block count for a system page is
   `ceil(factor · align8(stored) / 239)`, read backwards out of §5.3's
   construction rather than stated by it.
3. `SectionNameLength` in the §5.2 section-map record counts **bytes
   including the two-byte terminator**; the spec's own field-width
   column ("SectionNameLength x 2 [+ 2]") suggests characters. The
   corpus decides it: the first section's page list begins exactly
   `0x40 + SectionNameLength` bytes into the record.
4. `ACDBDICTIONARYWDFLT` writes one `TV` more than `numitems` on R14.
   §20.4.45 gives the class a default-entry *handle*, which costs no
   data-stream bits from R2000 on. One record type across three files
   is thin evidence for what the extra slot means, so it is consumed
   and deliberately left unnamed.

The trailing bit after `DIMLWE` that `tables::dimstyle` reads is
likewise measured — it was already measured on R2013/R2018 by an
earlier change, and the R2000 and R2004 records of this corpus need
exactly the same one bit. Two release bands agreeing on an undocumented
bit is the strongest statement available about it, so it is consumed
and not named.

The `src/r2007.rs` this PR replaces described R2007 as applying a
two-layer "Sec_Mask" — a byte XOR plus a 7-byte bit rotation. That
description matched nothing in the spec and nothing in the bytes; the
module and its tests are removed rather than kept as a misleading
scaffold.

## 2026-08-30 — Block-name ground truth (public DXF twin + AutoCAD DXF Reference vocabulary)

The PR for #70 settles which of two disagreeing readers carries a
block's real name. Two outside sources contributed, both public and
both allowed above:

- **`arc_2013.dxf`** from the `nextgis/dwg_samples` repository — the

  which the corpus already carries. It is a *data* file under the

  interoperability testing" clause, not documentation and not source.
  It is read only as an oracle: its `BLOCK_RECORD` table names handle

  was taken from it — the field list, the string-stream arithmetic and
  the handle-stream anchor are all derived from the DWG bytes and from
  §19.1 / §20.4.52 of the freely-redistributable ODA specification.
  The file is not vendored into this repository.
- **AutoCAD's anonymous-block naming convention** — `*D<n>`, `*T<n>`,
  `*U<n>` and `*Paper_Space<n>`, i.e. a family letter plus a decimal
  suffix — as recalled from Autodesk's public *DXF Reference*. This is
  published documentation, not SDK or product source, and it
  contributed **vocabulary only**: it is the reason the crate asserts
  that the difference between a BLOCK_HEADER's stored string and its
  `BLOCK` sentinel's name is always a decimal suffix. The assertion is
  independently measured (27 of 27 definitions on
  `sample_AC1032.dwg`), so the document supplied the name of the
  pattern, not the pattern itself.

The `§19.5.51` citation `src/tables/block_record.rs` previously carried
is withdrawn in favour of `§20.4.52`, which is where the ODA
specification prescribes BLOCK_HEADER.

## 2026-10-26 — DXF value oracle: pairing and field scorers

The PR for #101 and #102 adds `examples/dxf_oracle`, which pairs every DWG
record with the record of the same handle in AutoCAD's own DXF export and
compares each decoded field with the DXF group that carries it. For the
types ODA spec v5.4.1 prescribes, the group of each field is the one the
spec prints in its DXF column (§20.4.x, cited on every scorer). For the
rest (MTEXT's chunked text, the attribute subclass, LAYOUT's subclass
split, the defaults AutoCAD omits, the `^J` control-character notation,
the lineweight values), the group codes and conventions are those of
Autodesk's public *DXF Reference*, recalled; it is published
documentation, not SDK or product source. Every convention the scorers
apply is also measured on the exports and documented in `scorers.rs`.
The exports read are `nextgis/dwg_samples` (no licence stated) and the
`samples/` directory of `DomCR/ACadSharp` (MIT), fetched by pinned commit
and sha256 into a cache outside the repository; only those data files
were read, not ACadSharp's code or comments.

## 2026-10-26 — Class layouts the specification never prints: derived from AutoCAD's own output (maintainer's decision)

ODA spec v5.4.1 gives a field list for the fixed object types and for some
custom classes (§20.4), and none for the rest (MATERIAL, the dynamic-block
`BLOCK*` classes, `ACSH_*`, `DBCOLOR`, `SUN`, `DATATABLE`, `PDFDEFINITION` and
others). By the maintainer's decision of 2026-10-26, a layout the spec does not
print is learned from AutoCAD's own output, by this method and no other:

- **What is observed.** An AutoCAD-written DWG and AutoCAD's own DXF export of
  the same drawing: the pinned `nextgis/dwg_samples` and ACadSharp `samples/`
  twins listed under "Public corpus" (data files, fetched by pinned hash), and,
  once the project's agents have made them, controlled drawings made in
  AutoCAD that vary one property at a time, with their exports. A record's DWG bits are
  read against the DXF record of the same handle, paired by
  `src/dxf_reader.rs` and `examples/dxf_oracle`.
- **How a field is accepted.** A field list is kept only if both hold. It
  closes every record of the class exactly on the record's data-stream
  boundary on every release band in which the class occurs (the same
  self-validation as every other decoder: a list that lands anywhere else is
  wrong, never trimmed to fit). And each decoded value equals the DXF group that
  carries it in the twin, compared by handle, by a probe under `examples/` that
  exits non-zero on any disagreement or boundary miss. A field the DXF does not
  show has only its width claimed, is named `unknown_*` or positionally, and is
  recorded as unverified by value. A class whose layout cannot be closed on
  every record stays undecoded; no partial decoder is shipped.
- **What is never used.** Any third-party implementation of DWG or DXF: not
  LibreDWG, the ODA or Teigha SDK, or any Autodesk SDK (all banned above), and
  also not ACadSharp's or ezdxf's reading code, their comments, their tests or
  their derived data, which the permissive-licence allowance above would
  otherwise cover. The names of the DXF groups in the twin are observed data;
  any further vocabulary taken from Autodesk's public *DXF Reference* is
  disclosed on the class's own line and contributes names only.
- **Record of derivation.** Each class gets its own dated entry below this one,
